# TB-PARTIAL-EQ：相等比较模型的信任边界

对应[英文规则](partial-eq.md)。

规则版本：**conditional-posts-v2**。操作者本次更正取代此前将该边界仅作为
前提、统一假设其成立的解释。

## 依据与优先采用的方案

2026-10-12，依据操作者提供的 reviewer 评论进一步明确：
**并非所有实现 `PartialEq` 的 Rust 类型都符合 Verus 的相等模型**。
`T: PartialEq<U>` 不能推出 `<T as PartialEqSpec<U>>::obeys_eq_spec()`。
本边界规定条件性保证，不是宣称所有类型均符合模型的公理。

记准确配对的符合性谓词为 B、全部后置集合为 Post，两种方案的调用域不同：

| 方案 | 合同结构 | 调用域 |
|---|---|---|
| (1) 限制前置条件 | `requires B; ensures Post` | 每个调用者都须建立 B。 |
| **(2) 优先采用的默认方案** | `ensures B ==> Post` | 原调用仍合法，包括 !B 情况。 |

本流程在需要该边界时采用**方案 (2)**，保留原 Rust API 调用域。
方案 (1) 可用于明确限制调用域的 API 或 wrapper，但不是证明失败后的自动回退；
须另行获得操作者对该受限范围的批准并显式记录调用域，不能静默套到原 std API，
也不能把其结果报告成原调用域内的条件性保证。
本次澄清沿用 **conditional-posts-v2** 的语义及历史证明范围，不另行升级结论。

## 只有需要时，使用条件后置

如果有需要，将**该函数的全部后置条件**放在 `T::obeys_eq_spec() ==>`
右侧；不是所有函数都必须这样写。不需要这个边界的函数保留普通后置与原界限。

对适用的 `T: PartialEq<U>` 配对，将以下谓词记为 `B(T, U)`：

```rust
<T as vstd::std_specs::cmp::PartialEqSpec<U>>::obeys_eq_spec()
```

必要时使用准确接收者/Rhs 的限定写法，包括异类型比较，不能换成同类型或反向配对。
`B` 是保证成立的条件，不是 API 可被调用的条件。不得把 B 增加为 API 前置条件，
也不得默认所有 Rust 类型都符合模型。
保留原身份、签名、生命周期、trait bounds 及合法的原前置条件；
不能为了引入这个 guard 给无关 API 增加 `PartialEq`。

要求的结构示意如下：

```rust
ensures
    <T as vstd::std_specs::cmp::PartialEqSpec<U>>::obeys_eq_spec() ==> {
        &&& P1
        &&& P2
        &&& P3
    },
```

`P1`、`P2`、`P3` 表示完整后置集合，包括返回、内容及存在的 frame／写回条款。
不能只给返回关系加 guard，却把该函数其他项目后置留在蕴含之外。
可使用展开后等价的共享谓词，避免重复包裹相同 guard；固定 upstream vstd 合同不改。

若项目编写的继承模型条款已有容器条件 C，仍把该条件保留在外层元素 B 之内：

```text
B ==> ((C ==> P_inherited) && P_contents && P_frame)
```

不能改成 `(B && C) ==> (P_inherited && P_contents && P_frame)`，
否则 B 真而 C 假时就丢掉了内容及 frame 保证。不能由 B 推出 C、把两个标志
等同，或把继承条款留在 B 外。这是对全部项目后置加保护，不修改固定上游合同。

B 为真时，全部受保护保证必须成立；B 为假时，这些后置不提供保证，
但 Rust 调用不因此变得非法或被禁止。
模型联系缺失不授权直接断言 B、隐藏假设或把逻辑值相等当成 Rust 的 PartialEq。

## 专门的项目记录

在项目中专门维护 `trust_boundaries/TB-PARTIAL-EQ.md`，
不要只把边界埋在 `issues/` 或证明文件里。
记录边界 ID 和 **conditional-posts-v2** 版本、各受影响函数为何需要该边界、
准确谓词/类型配对、全部受保护后置、固定 vstd 模型定义和合同、
proof/query 的具体位置以及剩余义务。
逐 API 覆盖索引、两条证明链、review 裁定和最终报告都要链接该记录。
其他信任边界需要各自的记录及操作者明确批准，本规则不授予任意新增假设的权限。

## 验证条件性结论，而不是加强调用前提

Correctness 在原前置条件下检查实际源码或获准的忠实副本是否满足完整条件后置。
可在 B 成立的 proof-only 分支中使用既有 `eq`/`ne` 条件合同；
不假设目标后置，不修改 vstd，不新增公理，也不通过 `assume`/`admit` 跳过义务。

Completeness 必须明确实际检查的问题。记 `CondPost = (B ==> Post)`，
条件唯一性为：

```text
原前提 => 源码满足 CondPost
原前提 && CondPost(input, r1) && CondPost(input, r2)
    => (B ==> selected_outputs_equal(r1, r2))
```

使用 checker 支持的编码，并检查生成比较及 reexecute。
若独立的 analysis-only 适配入口用 B 作前提检查这个条件性结论，
必须显式标明这一检查范围；不能把适配入口的前提反过来加到 API 合同，
也不能称为无条件确定性。checker 无法表达时记录限制，不手改 query 或制造成功。

`!B` 时允许多个输出说明无条件唯一性不成立，不是条件性保证的反例；
要保留这个区别，而不是排除该 API 调用。
检查合法的 B 为真实例及 !B 时蕴含空真的行为；
错误或矛盾前提、零相关义务不能作为有用证明。
选用完整 guard 后，不自动把空输入/长度条款加到 guard 之外。

## 这个边界不保证什么

`eq_spec` 是元素比较模型，不是 Verus 的逻辑值相等。
该标志不提供自反性、对称性、反向类型配对的符合性、无内部状态修改、
调用顺序、短路行为或无 panic 保证；必要状态/效果观察仍属于受保护合同，
并需在 guard 成立时实际证明。
源码使用 `ne` 及字节比较特化时，仍需相应既有合同与源码对应。

假设容器比较符合自己的模型，不等于已经把容器的 `eq_spec` 定义为序列关系；
元素符合模型，也不自动证明容器符合模型。存在实际模型定义时应复用。
Cow Deref 的内容联系、私有字段/raw pointer 的表示对应、目标实现证明仍是义务。
不能借此假设目标后置，或新增内容/view 等式。

## 迁移与报告

对受影响的项目 API 合同，移除仅由旧规则添加的 B 前置，改成全部后置受同一蕴含保护。
保留无关安全前提与无关函数；同步受影响客户端和证明输入，
保留旧候选/结果及它们准确的规则版本。前后置变化需要相应的 correctness
和条件 completeness 审阅，旧的仅在前提 B 下通过不自动等于新 API 合同通过。

结果标记 **verified under TB-PARTIAL-EQ (conditional-posts-v2)**，
区分条件完整性与无条件确定性。原 canonical 清单不变，迁移同一 API 不重复计数。
旧 `UNKNOWN`/失败不自动变成通过；旧成功保留历史范围，实际检查迁移后才能采用新口径。
本次规则更正不证明缺失源码桥接，也不授权修改工具或 implementation。
